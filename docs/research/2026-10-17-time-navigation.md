日期：2026-10-17。目标：为现有紫微命盘增加大限 → 流年 → 流月 → 流日 → 流时的连续选择，保留本命入口与当前排盘口径。本文件是研究记录，不作为发布成功证明。

本轮使用 `xinghuo` 调研工作流，并读取 Agent Reach 主技能与 search / social / dev / web / video 五份参考。只读公开资料与本机依赖，向实现成员反馈核验结果；调研过程未发布、发帖、私信或操作社交账号。Gemini / ChatGPT 提示词仅供手动运行，未冒称已经执行深度研究。

## 1. 结论与入口选择

最合适的入口是**现有命盘 + 官方运限数据结构 + 明确的时间归一化适配**。本机实际安装 `iztro 2.6.1`、`lunar-lite 0.2.8`；在线官方文档已展示 `2.6.2`，不能把新版的配置隔离保证直接当作已安装版本的行为。现有应用还有自己的四化、亮度、日期规范化与宫位索引，增加导航时应保留这些既有口径。

## 3. 官方资料与可复用实现

### 数据结构与版本

[官方运限文档](https://docs.iztro.com/posts/horoscope)说明运限由星盘的 `horoscope(date, timeIndex)` 获取，而非手工构造功能对象；五层分别是 `decadal`、`yearly`、`monthly`、`daily`、`hourly`。当前在线页明确把“沿用星盘创建时配置”的保证标为2.6.2。本机2.6.1仍在查询时读取全局配置；见后面的实际差异测试。

[2.6.1发布记录](https://github.com/SylarLong/iztro/releases/tag/v2.6.1)包含显式时辰0、晚子分界和虚岁相关修复，说明这些属于已发生过的真实边界问题，测试必须显式覆盖0，不能写 `hour || defaultHour`。

已核对 [2.6.1 FunctionalAstrolabe 源码](https://github.com/SylarLong/iztro/blob/v2.6.1/src/astro/FunctionalAstrolabe.ts)及本机编译产物。各层包括命宫位置 `index`、干支、重排 `palaceNames`、四化 `mutagen` 和流曜；四化顺序是禄、权、科、忌。本机已有 `decadalList()`、`yearlyList(indexOrName)`、`monthlyList(year, fixLeap)`，适合核验导航候选项。

`monthlyList(year,true)`从真实农历年取得月份与天数；普通年12项，含闰月且拆分前后半月时14项，不拆分时13项。月段带 `isLeapMonth`、`part` 和 `dayRange`。不能把所有年份写死成12个公历月份。

本项目宫位数组与 iztro 的“从寅起”索引不是同一个编号体系。应先建立显式映射，再高亮命宫、三方四正及四化星曜，不能直接用源 `index` 访问按地支子起排列的数据。

### 月、日、时分界

[lunar-lite 作者源码](https://raw.githubusercontent.com/SylarLong/lunar-lite/main/src/ganzhi.ts)与本机0.2.8一致：`normal` 的年干支取农历年；流月干支用五虎遁，并对闰月十六日开始加一月。宫位推进和干支推进都需处理闰月后半段。`exact` 的月份走节气方法；本轮不在功能扩展中隐式切换该口径。

同一实现以时辰索引构造代表时刻：0为00:30，1为01:30，……，12为23:30；日干支采用晚子相关方法。现有应用已经将真太阳时和晚子时归入排盘日期，因此导航若接受“归一化日期 + 0..11”，不应再次将子时当作12传入并重复换日。需在界面说明此处选择的是排盘时辰，而不是未经校正的出生钟表读数。

### 可借鉴的官方界面

[react-iztro README](https://github.com/SylarLong/react-iztro/blob/main/README.md)提供五层显示、重排宫名、运限四化与动态三方线。源码进一步显示两个可复用设计：

- [Iztrolabe.tsx](https://raw.githubusercontent.com/SylarLong/react-iztro/main/src/Iztrolabe/Iztrolabe.tsx)：目标日期/时辰与层级显示分离；三方线取当前最细可见层，顺序为流时、流日、流月、流年、大限。
- [IzpalaceCenter.tsx](https://raw.githubusercontent.com/SylarLong/react-iztro/main/src/IzpalaceCenter/IzpalaceCenter.tsx)：时辰在0..11之间步进并跨日，日期可以前后移动。不过月按钮使用公历 `Date.setMonth`，并非真实农历流月段导航；这部分不能直接照搬。

没有运行这些组件、确认在线演示或评价其手机实际交互。以上是源码观察，不是浏览器验收结论。

## 4. 本轮最小实测

全部使用合成日期，无个人资料。命令在独立 Node 进程中读取本机已安装包，不改变正在运行的应用进程配置。测试基盘统一为 `astro.bySolar('1996-6-18',5,'女',true,'zh-CN')`，索引保留 iztro 原始编号。

| 检查 | 输入 | 实际输出 | 对实现的含义 |
| --- | --- | --- | --- |
| 闰月前后段 | 2023闰二月15 / 16，经 `lunar2solar` 换算 | 2023-04-05：流月乙卯，月命宫3，日命宫5；2023-04-06：丙辰，月命宫4，日命宫7 | 月干支和月宫位同时变化；不可只改宫位 |
| 显式时辰0 | 2026-10-17，timeIndex=0 | 日甲子、时甲子，日宫8、时宫8 | 0是有效输入，不能被真假值判断吞掉 |
| 其他时辰 | 同日timeIndex=1 / 11 | 1：甲子日乙丑时，时宫9；11：甲子日乙亥时，时宫7 | 时辰选择必须真正改变时层 |
| 晚子原始接口 | 同日timeIndex=12 | 日乙丑、时丙子，但日宫仍8、时宫8 | 原始日期+12与隔日0不能不经核验就宣称整层等价；本项目应遵守先归日的约定 |
| 2.6.1全局配置漂移 | 同一星盘查询2026-02-10；先normal，再仅改变全局horoscopeDivide为exact | 年乙巳/月己丑 → 年丙午/月庚寅 | 新导航应锁定已选口径，不能依赖新版才有的实例配置保证 |

已将闰月干支、晚子边界与全局配置实测反馈给引擎实现成员。没有在本次研究中完成新导航浏览器验收、线上部署、第三方排盘全样本比对或命理预测准确性验证。

## 5. 对当前项目的具体实施建议

以下是结合官方代码和本项目现状提出的实现设计，不宣称已经全部写入产品：

1. 用一个明确的目标日期与时辰派生全部五层。层级切换只改变当前阅读层，不能偷偷重排出生资料或覆盖本命盘。五行局与主星位置仍来自原图。
2. 大限行取真实 `chart.daXians` 与起止虚岁；流年行取选中大限范围。农历年号和公历日期应分别命名，避免春节前被公历年份误导。
3. 流月行展示真实月份，闰月需要明确前后半段。流日候选依该段真实天数生成；选择上一级后，保留仍有效的下级，否则选首个有效项，避免不存在的三十日或闰月残留。
4. 流时使用明确0..11索引及对应时辰名。日/时前后按钮要处理跨日，限制支持范围；“回到今天”同时更新完整选择状态。
5. 当前层驱动动态命宫、宫名、三方四正和该层干支四化；本命四化保留可区分的样式。不要让月份按钮只变标题，而盘面仍显示固定流年结果。
6. 将计算数据与交互组件分离；纯计算适配层可用官方 `horoscope()` 和列表方法作对照，验证宫位、干支、四化而非只验证按钮文字。
7. 如暂不升级2.6.1，隔离配置依赖并把口径写入适配层。升级2.6.2是独立变更，应核对锁文件与既有排盘回归，不作为“顺便更新”。

有意义的验收范围：大限边界、春节前后、闰月十五/十六、月末、农历大小月、流时0与11跨日、出生前日期、输入上界、切换命盘后的状态重置、移动端五行选择不溢出，以及选中层确实改变盘面。对于尚未覆盖的边界应直接列出，不能用构建通过代替算法一致性。
